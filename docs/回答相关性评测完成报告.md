# 回答相关性评测（LangSmith Evaluation 第五阶段）完成报告

**阶段目标**：只新增 **一个** LLM-as-a-Judge —— 回答相关性 `rag_answer_relevance`。
不并行引入 Faithfulness / Citation correctness / Answer correctness / 多指标聚合 / Prompt 优化，
先把一个 Judge 做通、做对、做可解释。

**结论**：`rag_answer_relevance` 已接入 LangSmith Evaluation，与既有的五个检索指标**完全隔离**
（各自独立实验、各自独立 evaluator 列表、不合成总分）。判定输入严格只有「用户问题 + Agent 最终回答」，
Judge 复用项目既有 LLM 配置（仅把温度固定为 0），判不出来一律记 `score=None` 而**不是 0 分**。

## 二、Judge 的输入与输出

### 输入（严格两项）

| 来源 | 字段 |
|---|---|
| Example | `inputs["question"]`（用户问题） |
| Run | **Agent 最终回答** |

**刻意不把检索到的文档作为判定依据**。检索片段是 Faithfulness / Citation 一类指标的输入；
本指标只回答一个问题——「这段回答是否针对用户提出的问题」，不做任何事实性判断。

### 最终回答在 Run 里的位置（实测核对，不是猜的）

真跑一轮知识问答后，从平台上读回**生产 root run**（`campus-flow.turn`），其 `outputs` 键恰为：

```
["error", "intent", "messages", "session_id", "sources"]
```

即回答在 **`messages` 里最后一条 `type == "ai"` 且内容非空的消息的 `content`**；
工具调用那一轮的 AI 消息 `content` 为空，必须跳过。
生产 root run **没有独立的 `answer` 字段**（此前看到的 `{retrieved, sources}` 是**检索评估 target 的输出**，
那个 Run 刻意不调用模型，因此根本不含回答）。

**数据缺口如实记录、不靠改上游掩盖**：本阶段**不修改** 节点 / 图 / RAGService 去补一个 `answer` 字段，
而是让 `extract_run_answer()` 兼容两种形状：

1. 优先读 `outputs["answer"]`（评估 target 显式给出回答的形状）；
2. 回退读 `outputs["messages"]`（生产 root run 的形状）。

两种都拿不到非空回答 → `unreadable = "缺少最终回答"`；
Run 报错 / 输出不是对象 / 结构非法 → 带诊断信息的 `unreadable`（与「缺回答」区分开）。

### 输出（结构化）

```
AnswerRelevanceVerdict -> {"score": 0.0~1.0, "reason": "<一句中文判定理由>"}
```

- 结构化输出沿用项目既有手法 `with_structured_output(..., method="function_calling")`，
  与 `app/agent/intent.py` 完全一致——DeepSeek 不接受 `json_schema` 响应格式，function calling 才是通吃方案。
- 评估器最终返回 LangSmith 标准契约 `{key, score, comment}`，其中 **`reason` 直接进入 `comment`**。
- 结构化输出**只绑定一次**：若模型/供应商不支持 function calling，绑定失败即永久标记不可用，
  不会每条用例都产生一次注定失败的调用。

### 失败语义（关键）

| 情况 | 返回 |
|---|---|
| Run 缺最终回答 | `score=None`，`comment="无法判定：缺少最终回答"` |
| Example 缺 `inputs.question` | `score=None`，`comment="无法判定：Example 缺少非空的 inputs.question"` |
| Judge 调用失败 / 抛异常 | `score=None`，`comment="无法判定：<原因>"`（**不让单条判定失败拖垮整轮评估**） |
| Judge 返回越界 / 非数字 / 布尔分数 | `score=None`，`comment` 里同时保留「越界分数 x」与模型理由 |
| Judge 判定成功 | `score=<0~1>`，`comment=<reason>` |

**判不出来记 `None`、绝不记 0 分**：0 分表示「确实答非所问」，两者含义完全不同，
混在一起会把基础设施故障伪装成回答质量问题。`None` 在 LangSmith 里记为 `n=0`，不参与聚合均值。

### Judge 模型

- 复用项目**既有** LLM 配置：`build_llm()` 提供 provider / model / api_key / base_url / timeout / max_retries。
- 唯一参数调整：`model_copy(update={"temperature": 0.0})`——判定要可复现。
- **没有第二套模型配置**。
- 与业务模型是**两个实例**：Judge 不共用业务 Agent 的那次调用，判定是**独立调用**。

## 三、评分档位（写进 system prompt，档位即契约）

| 分数 | 含义 |
|---|---|
| **1.0** | 完全针对问题，直接回答核心需求 |
| **0.7 – 0.9** | 基本回答了问题，但存在少量无关内容或遗漏 |
| **0.4 – 0.6** | 只部分回答了问题 |
| **0.1 – 0.3** | 大部分没有回答问题 |
| **0.0** | 完全没有回答问题 / 答非所问 |

补充规则（同样写进 prompt）：

1. 这是**回答相关性**判断，不是事实正确性判断——**不因为回答里的内容可能有误就给低分**；
   只要它确实围绕用户的问题作出了回应，就按档位给分。
2. 回答若明确说明「知识库中没有相关资料」但仍在回应用户所问的方向，**不直接判 0 分**。
3. 不臆测用户没问过的需求，也不把回答长度当质量。
4. `reason` 用一句中文说明打分依据（引用回答中的关键表述，不复述整段回答）。

## 六、遗留问题

1. **只验证了 2 条**（`library-hours` + `gym-hours`），**未跑全量 15 条**。
   该入口刻意**不提供全量模式**（`--evaluate-rag-answer` 与 `--langsmith-full` 同用 → 参数错误 exit 2）：
   回答相关性会真实调用模型，全量执行应当是一次显式决定。
2. **生产 root run 仍没有独立 `answer` 字段**（数据缺口如实记录，靠 `messages` 末条 AI 消息回退读取）。
   若将来要给评测 / 前端提供稳定字段，需要在 knowledge 节点补写——属上游变更，本阶段不做。
3. **Judge 是绝对分档**，随 Judge 模型与提示词版本漂移；换 Judge 模型或改档位描述后需重新抽几条样本标定。
   分数只能同版本内纵向比较。
4. **回答由 `RAGService.answer` 生成，而非完整图**：差异仅在意图路由那一步
   （对 knowledge 类问题不产生影响，检索与生成链路逐字相同）。若要连路由一起评，需另建目标函数。
5. 分数未知（`None`）的条目在 LangSmith 侧记为 `n=0`、不进均值；若大量判不出来，
   报告只会显示「(无有效分数)」——需要人工留意，不会自动告警。
6. 本阶段**未做**（明确留给后续）：Faithfulness、Citation correctness、Answer correctness、
   多指标聚合视图、Prompt 优化、Prompt Management。
