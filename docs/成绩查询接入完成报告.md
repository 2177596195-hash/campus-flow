## 2. 数据库表结构

```sql
CREATE TABLE IF NOT EXISTS score (
    id         BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
    student_id VARCHAR(64)  NOT NULL COMMENT '学号',
    semester   VARCHAR(32)  NOT NULL COMMENT '学期，形如 2025-2026-1',
    course     VARCHAR(128) NOT NULL COMMENT '课程名称',
    -- 用 DECIMAL 而不是 FLOAT / DOUBLE：成绩是「精确的十进制数」，
    -- 二进制浮点会出现 91.5 -> 91.499999... 这类表示误差，
    -- 直接比较与加权计算都会踩到。DECIMAL(5,2) 覆盖 0.00–999.99。
    score      DECIMAL(5,2) NOT NULL COMMENT '成绩分数（0-100）',
    -- 学分同样是十进制数（常见 0.5 的倍数），DECIMAL(3,1) 覆盖 0.0–99.9。
    credit     DECIMAL(3,1) NOT NULL COMMENT '学分',
    created_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    PRIMARY KEY (id),
    -- 自然唯一键：同一学生在同一学期、同一门课只有一条成绩。
    -- 它同时让 data.sql 可以用 INSERT IGNORE 写成幂等种子脚本。
    UNIQUE KEY uk_score_student_semester_course (student_id, semester, course),
    -- 查询恒为「按学号取某人成绩」，因此建学号索引。
    KEY idx_score_student (student_id),
    -- 「某学期的成绩」是主要过滤条件；联合索引让「学号 + 学期」一次命中。
    KEY idx_score_student_semester (student_id, semester)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_general_ci COMMENT = '学生成绩';
```

设计与既有约定一致，几处**有意为之**：

1. **`score` / `credit` 用 `DECIMAL` 而非 `FLOAT` / `DOUBLE`**
   成绩是精确十进制数，二进制浮点把 `91.5` 存成 `91.499999...`，会让相等判断
   出现意外并在加权时放大误差。Java 侧 `BigDecimal`（便捷 `double` 构造器走
   `BigDecimal.valueOf`，按十进制表示转换，不引入二进制误差），
   整条链路不经过二进制浮点。
2. **学期进唯一键**：同一门课可能**重修**，那是「两条记录的两件事」，
   不是同一条被覆盖。
3. **没有 `exam_type` 字段**：当前需求不需要区分考试类型，按「不凭空增加无意义
   字段」的原则不加；将来若要做「平时分/期末分分别查询」，再加列并同步唯一键。
4. **`semester` 存 `VARCHAR(32)`**：格式 `2025-2026-1` 定长，字典序与时间序一致
   （因此可直接 `ORDER BY semester DESC`）；不引入日期解析开销。

### 种子数据（7 行）

| student_id | semester | course | score | credit |
|---|---|---|---|---|
| student-001 | 2025-2026-1 | 数据结构 | 92.00 | 4.0 |
| student-001 | 2025-2026-1 | 计算机网络 | 88.00 | 3.0 |
| student-001 | 2025-2026-1 | 操作系统 | 95.00 | 3.5 |
| student-001 | 2024-2025-2 | 高等数学 | 84.00 | 5.0 |

③ 同学期多门课；④ 学分非整（3.5）与非 `0.5` 倍数以外的常见值。

## 3. API

```
GET /api/scores?studentId=student-001
GET /api/scores?studentId=student-001&semester=2025-2026-1
```

- `studentId`：**必填**。缺失时由 Spring MVC 自动返回 400。
- `semester`：**可选**（`required = false`）。不传即返回该学生全部成绩；
  传了只返回该学期的成绩（`semester = ?` **精确匹配**，不做前缀/模糊匹配）。
  「空白视为未提供」的归一化在 Service 层做（属于业务语义）：
  `?semester=` 这种空值是调用方笔误，若按字面匹配，返回的空列表会被误读成
  「这学期没有成绩」。
- **查不到返回 `[]`，HTTP 200**，不设计成异常（该学生/该学期没出分是正常结果）。

响应体（DTO，只含 4 个字段）：

```json
[{"semester":"2025-2026-1","course":"数据结构","score":92.00,"credit":4.0}]
```

- `score` / `credit` 保持**数值类型**（`BigDecimal` 经 Jackson 序列化为 JSON 数字），
  不做字符串化——模型要能直接比较大小与做加权。
- 实体内部字段 `id` / `studentId` / `createdAt` 一律不出现（有专门用例守住）。
- 排序：`semester DESC, course ASC`（先看当前学期；同学期按课程名）。

## 4. Python 改动

### 4.1 `CampusApiClient` 新增 `fetch_scores`

```python
SCORE_PATH: Final[str] = "/api/scores"          # client.py

def fetch_scores(self, student_id=None, semester=None) -> list[dict[str, Any]]:
    target = student_id or self._default_student_id
    params: dict[str, str] = {"studentId": target}
    if semester is not None:                     # None 时省略该参数，不发空值
        params["semester"] = semester
    payload = self._get_json(SCORE_PATH, params=params)
    return self._expect_records(payload)
```

**没有新建第二个 HTTP Client**：基址、超时、错误分类、JSON 解析、回环直连
（`_direct_mounts`）全部沿用既有实现，并复用已抽出的 `_expect_records`（数组结构校验）。
`__init__.py` 补导出 `SCORE_PATH`。工具层不感知 `student_id`（由 `CAMPUS_STUDENT_ID` 决定）。

### 4.2 `score_tools.py`：删除 mock，改走真实链路

**删除**原 `_SCORE_TABLE`（写死的成绩字典）与 `KNOWN_SEMESTERS`（写死的学期白名单），
函数签名与返回结构**保持不变**：

```python
target_semester = _clean_text(semester, name="semester")
target_course = _clean_text(course, name="course")
rows = get_campus_api_client().fetch_scores(semester=target_semester)   # 学期过滤在服务端
normalized = normalize_score_rows(rows)
selected = normalized if target_course is None else [r for r in normalized if _match_course(...)]
return selected
```

**两个参数的处理方式不同，这是刻意的：**

- `semester`：**查询下推**。过滤在服务端完成，工具只把条件透传成 query 参数。
  学期是数据库里的一列，「哪些学期有成绩」属于业务事实，在客户端再判断一次就是
  第二份事实来源——因此删掉了写死的 `KNOWN_SEMESTERS` 白名单。
- `course`：**本地挑选**。接口契约只按学号+学期筛选，「某门课的成绩」是在取回的
  那一小段列表里再做一次课程名匹配（双向包含，容忍模型把「某课」补全成「某课课程」）。
  这与课程表工具「按周过滤属于服务端」并不矛盾：周次过滤需要数据库做范围比较并走索引，
  课程名匹配只是一次针对几条记录的挑选。

保留不变的部分（有意为之）：`CURRENT_SEMESTER = "2025-2026-1"`（**教务日历常量**，
用于让模型把「这学期/本学期」映射成具体学期，不是成绩数据）、`_clean_text`（剔除
不可见字符 BOM/零宽 + 空串视为未提供 + 类型校验）、`_match_course`、
`logger = logging.getLogger(__name__)`、`__all__`。

### 4.3 新增 `score_contract.py`

与 `exam_contract.py` / `course_contract.py` 同构：`SCORE_FIELDS` +
`normalize_score_row/rows`，把字段定义与归一化集中一处，工具本体保持「薄」。

**与其他两个契约的关键差异：成绩与学分是数值，不是字符串。**

- `SCORE_FIELDS = ("semester", "course", "score", "credit")`，
  `NUMERIC_FIELDS = ("score", "credit")`；`score` / `credit` 输出 `float`。
- `_as_number()`：显式**拒绝 `bool`**（`bool` 是 `int` 子类，`true` 不是成绩）、
  拒绝 `NaN` / `Infinity`；接受 JSON 数字（`int`/`float`）与数字字符串。
- 刻意不做范围校验（0–100）：那是业务有效性，不是接口结构问题；契约只负责
  「类型对不对、能不能用」。
- 异常沿用 `CampusServiceDataError`，调用方（`handle_tool_error`）无需新增分支。

### 4.4 测试替身 `_fakes.py`：按路径路由 `/api/scores`

`DEFAULT_CAMPUS_PAYLOADS` 新增 `SCORE_PATH: score_stub_response`；
`score_stub_response(request)` 读取 query 里的 `semester` 做与服务端一致的过滤
（若替身对任何 `semester` 都返回同一份数据，「参数真的传下去了」就测不出来）；
`TOOL_MODULES_WITH_CAMPUS_CLIENT` 增加 `"app.tools.score_tools"`，

## 8. 遗留问题

1. **`CURRENT_SEMESTER = "2025-2026-1"` 仍是 Python 侧常量。**
   它是**教务日历**概念（用于让模型把「这学期/本学期」映射成具体学期），不是成绩数据，
   因此本阶段没被删除；但严格说它同样应由服务端（校历接口）提供。
   与课程表工具的 `CURRENT_WEEK = 3` 是同一类问题，接入校历后应替换为一处配置或校历接口。

2. **`student_id` 仍绑配置值**（`CAMPUS_STUDENT_ID`，默认 `student-001`），
   尚无登录态/多用户身份；`student-002` 只能通过环境变量或直接调接口来验证。

3. **`KNOWN_SEMESTERS` 白名单已删除**，学期存在性改由服务端按 DB 精确匹配承担
   （查不到返回空列表而非错误）。好处是消除了「哪些学期存在」的第二份事实来源；
   代价是模型若把用户口语映射成不存在的学期，用户会看到「该学期没有成绩」
   而不是「学期名写错了」——这是可接受的语义词退化。

4. **`score` 只有单次成绩，未建模补考/重修记录**。当前「同学期同课程唯一」，
   若将来需要「首次考试成绩 vs 补考成绩」并存，需要加 `exam_type` / `attempt`
   字段并调整唯一键（与第 2 项的重修语义相关）。

5. **`normalize_score_row` 不做数值范围校验**（如 0–100）：契约只保证类型可用，
   越界数据应在数据侧暴露，而不是在这里被悄悄改写或拒绝。

6. **无缓存 / 无重试熔断 / 无分页 / 无鉴权**：每次提问都是一次实时 HTTP 查询；
   成绩数据量小，本阶段不需要，但接入真实规模后需要评估。

7. **`mvn` 不在 PATH**：本机 Maven 走 IntelliJ 内置
   （`D:\idea\IntelliJ IDEA 2025.3.1\plugins\maven\lib\maven3\bin\mvn.cmd`），
   直接 `mvn ...` 会「命令不存在」且**静默失败**（若用后台任务，退出码可能仍为 0）。
   打包/测试必须用完整路径调用。已记入项目记忆。

8. **`mvn package` 前必须先停服务**：运行中的进程占用 jar，repackage 会因
   `Unable to rename ...jar to ...jar.original` 失败。本阶段真实联调前先
   `Stop-Process` 停掉旧服务，再打包、再重启。

9. **`campus_test` 库不随启动自动建表**（`sql.init.mode=never`），
   新增 `score` 表后必须手动应用 `schema.sql` 到测试库，否则 Java 用例报
   「表不存在」。这是既有设计（避免测试互相 DDL），但新增表时容易踩。
